# Comparative Review

## Comparable Patterns

| Draft C decision | Comparable system pattern | Assessment |
|---|---|---|
| `events.ndjson` is canonical; `state.json` is a projection | Temporal treats workflow event history as the durable source of truth; Vercel Workflow records inputs and outputs in an event log and replays deterministically after crashes or deploys; Inngest persists step results in managed state and resumes incrementally [1][2][15][16][17] | **Stronger for local inspectability, weaker for operational reach.** Draft C makes the truth visible and portable on disk, which is excellent for a CLI-first product. But Temporal/Vercel/Inngest prove that once history is authoritative, the hard part is not logging events, it is defining replay, timers, waiting, and concurrent mutation semantics precisely. Draft C is making the right foundational choice, but it has not yet specified the replay contract tightly enough. |
| Every dispatch attempt gets an immutable filesystem boundary | Vercel compiles each durable step into an isolated route; Inngest executes each step as a separate HTTP request and memoizes successful step state; GitHub's artifact model moved toward immutable archives with unique IDs to avoid accidental corruption [10][15][16][18] | **Mostly stronger for AI-agent workflows.** LLM work benefits from preserving prompt headers, prompts, handoffs, and retry context per attempt. Mature systems converge on isolation too, but usually at the process, route, or artifact boundary rather than a human-readable directory tree. Draft C is not reinventing isolation; it is specializing it for inspectable agent work. |
| Named outputs are the dataflow layer, not conversational memory | GitHub Actions requires explicit `jobs.<job_id>.outputs` and `needs.<job_id>.outputs.*`; Argo DAG tasks declare dependencies; Dagster emphasizes declarative dependencies and lineage between assets [3][5][6][11] | **Stronger than ad hoc string passing, but weaker where reduction is implicit.** Draft C is aligned with established workflow practice in insisting on explicit producer/consumer edges. The weak spot is that `first-clean` and especially `merge-digests` hide fan-in behavior inside binding policy instead of making the reduction step explicit. |
| There are only `dispatch`, `interactive`, and `pipeline-execute` action types | Temporal separates durable orchestration code from Activities; Vercel distinguishes `'use workflow'` orchestration from `'use step'` units of work; Inngest uses `step.run()` for durable retriable units and memoized transforms [2][15][16][18] | **Weaker than prior art.** Every serious durable-execution system distinguishes "the orchestrator's own computation" from "external/effectful work". Draft C's missing `synthesis` step is not a small schema gap; it is a missing architectural category. |
| Human gates are explicit runtime objects | GitHub environments can hold jobs in a waiting state until required reviewers approve; Prefect distinguishes pausing from suspending and supports typed human input; Vercel provides hook-based resume points [7][8][13][14][18] | **Conceptually stronger, operationally weaker.** Draft C is right to model approvals and manual tests as state, not prose. But GitHub/Prefect/Vercel all make the wait mode explicit: waiting, approved, rejected, timed out, resumed. Draft C still overloads too much into `waiting_for_gate` vs `blocked`, so its operator story is not yet as crisp. |
| Default parallel join preserves sibling work instead of failing fast | Argo DAG defaults to `failFast: true`, but allows turning it off so branches can finish; GitHub job outputs are only available through explicit dependencies after the producing job completes [5][11] | **Stronger for research and review methods.** For comparative, design, and review workflows, partial results from a "losing" branch are often still valuable. Draft C's instinct to preserve sibling handoffs is better suited to knowledge work than Argo's default. The missing piece is a clear rule for when partially completed outputs become consumable. |
| Locking is mentioned but not designed | Argo has mutexes and semaphores with explicit blocking behavior; Dagster differentiates deployment-wide and run-local concurrency controls; GitHub supports named concurrency groups with optional cancel-in-progress behavior [4][9][12] | **Weaker than prior art.** A single `run.lock` is enough to protect a local mutator, but not enough to express semantic resource ownership. Mature systems separate filesystem integrity from workflow-level concurrency policy. Draft C currently conflates them. |
| Template selection falls back to "runner intent mapping" inferred from prose | Temporal, Inngest, Argo, GitHub, and Dagster generally make execution mode explicit in code or config instead of inferring it from titles and descriptions [2][5][11][15][18] | **Arbitrary and avoidable.** This is the least defensible choice in the draft. Mature systems do not usually guess whether something is "research" or "implementation" from prose because inference makes resume, audit, and migration less stable. |

The biggest meta-pattern is this: mature workflow engines separate four concerns very aggressively: durable history, explicit dependency edges, isolated execution units, and first-class wait states. Draft C already has the first three instincts, but its current schema and state model do not yet encode them as precisely as the best prior art does [1][2][11][13][18].

I did **not** find strong prior art for one specific Draft C choice: making a human-readable, attempt-isolated filesystem tree the primary public runtime contract. The closest analogues are Argo's pod/artifact boundaries and GitHub's immutable artifacts, but Draft C's `.method/` directory is more inspectable than either. That looks like a deliberate product choice, not a reinvention error.

## Tradeoffs vs Draft

The most important tradeoff is **local-first transparency vs managed durable execution**. Temporal, Inngest, and Vercel all hide persistence behind services that own queues, timers, and replay. Draft C instead exposes the control plane on disk. That is favorable for a CLI-first method runner because humans and agents can inspect causality directly, but it means Draft C must specify behavior that those platforms bake into infrastructure: replay determinism, stale-lock handling, waiting semantics, and state transitions [1][2][15][17][18].

The second tradeoff is **artifact explicitness vs execution convenience**. Draft C's named outputs are structurally closer to GitHub job outputs, Argo DAG dependencies, and Dagster lineage than to prompt-chaining. That is a real strength. The cost is that the draft cannot get away with fuzzy resolution rules. Once outputs are the contract, parallel fan-in, shadowing, merge behavior, and output availability timing all need to be specified like API semantics, not "best effort" runtime behavior [3][5][6][11].

The third tradeoff is **research-friendly joins vs operational fail-fast defaults**. Argo defaults to fail fast because infrastructure pipelines usually want to stop spending resources once the DAG is doomed. Draft C is aiming at design, research, implementation, and review methods, where the losing branch often still contains valuable evidence. Preserving sibling handoffs is a better default for this domain. But that stronger default only works if downstream consumers see a stable join boundary and never race partially materialized outputs [5][11].

The fourth tradeoff is **adapter neutrality vs platform affordances**. GitHub Actions and Vercel Workflow get a lot of behavior "for free" because the platform defines their runtime boundaries. Draft C wants the method model to outlive any adapter, which is the right long-term product bet. The cost is that the adapter interface has to be more explicit than the draft currently makes it. Otherwise Claude Code assumptions leak back in through template inference, handoff parsing, and interactive-step behavior [7][13][18].

## Where the Draft is Stronger

- The event-sourced plus filesystem design is more inspectable than Temporal, Inngest, or Vercel. For a developer-facing method runner, being able to open `events.ndjson`, `attempt.json`, prompt headers, and parsed handoffs is a meaningful product advantage, not just an implementation detail [1][2][15][17][18].
- Attempt isolation is unusually well-suited to LLM workflows. GitHub and Argo isolate jobs; Draft C isolates the exact prompt-and-handoff boundary that actually matters when retries must be audited and corrected [10][11].
- The insistence that named outputs replace conversational memory is the right architectural move. It pulls the system toward explicit dataflow instead of prompt archaeology, which is where mature workflow systems have already converged [3][5][6][11].
- Preserving sibling results by default is a better fit for comparative and review methods than Argo-style fail-fast defaults. This is one of the places where Draft C is making a domain-specific choice that is genuinely better for its workload [11].
- Treating the method model as the product, with Claude Code as only the first adapter, is strategically stronger than GitHub Actions or Vercel-style platform entanglement. That is the right direction if Capacitor is meant to become the durable runtime later [1][18].

## Where the Draft is Weaker

- The missing `synthesis` action makes the schema less complete than Temporal/Vercel/Inngest, all of which clearly separate orchestrator-owned durable logic from effectful execution units [2][15][16][18].
- The state model is under-specified compared with mature engines. Temporal in particular shows how exhaustive event vocabularies and execution histories reduce ambiguity in retries, timeouts, and terminal states [2].
- Gate semantics are too fuzzy. GitHub distinguishes waiting, approved, rejected, and failed deployment states; Prefect distinguishes pause from suspend and ties suspend to persisted state. Draft C needs the same kind of crispness [7][8][13][14].
- Locking is not yet serious enough. Argo, Dagster, and GitHub all expose named concurrency control with visible blocking semantics; Draft C currently only gestures at a `run.lock` [4][9][12].
- Template intent inference is weaker than explicit metadata. It creates non-determinism at exactly the layer that should be most stable under resume and migration.
- Parallel output availability is too implicit. Mature systems usually make the join boundary or dependency edge explicit; Draft C still leaves too much up to interpretation [5][11][17].

## Adopt or Avoid Recommendations

- **Adopt:** Add a first-class `synthesis` action type. It should represent runner-owned computation that consumes named artifacts and emits named artifacts. This is the cleanest fix for the current schema hole and the best way to keep `merge-digests` from becoming hidden control flow. Model it more like Temporal workflow logic or Vercel/Inngest orchestration than like another dispatched worker [2][15][16][18].
- **Adopt:** Define explicit attempt and step state machines. At minimum, distinguish created, dispatching, running, handoff-detected, handoff-parsed, output-bound, waiting-for-input, waiting-for-gate, completed, failed, and blocked. Temporal's event-history discipline is the right standard here: legal transitions should be machine-checkable, not prose-only [2].
- **Adopt:** Split gate outcomes into at least `waiting`, `approved`, `rejected`, `timed_out`, and `validation_failed`. Also distinguish a `pause`-style wait from a `suspend`-style wait. Prefect's pause vs suspend split is especially instructive because it maps directly to Draft C's CLI-now / Capacitor-later environment story [13][14].
- **Adopt:** Reserve output binding for selection, not reduction. `single` and `all` are fine. `first-clean` is acceptable if its ordering rule is explicit. `merge-digests` should either become a real `synthesis` step or be restricted to a deterministic runner-generated summary artifact. Do not hide LLM synthesis inside binding resolution [5][11].
- **Adopt:** Introduce logical artifact IDs and digests in addition to paths. GitHub's artifact model is useful here: immutability gets much easier to reason about once every artifact has an ID, digest, and overwrite story independent of its storage path [6][10].
- **Adopt:** Separate `run.lock` from semantic workflow locks. Keep `run.lock` as a local mutator guard, but add named mutex/semaphore semantics for shared resources or cross-run coordination. Borrow Argo's explicit blocking semantics and GitHub's named concurrency-group idea [9][12].
- **Adopt:** Replace "runner intent mapping" with explicit metadata. Add a small `intent` or `mode` enum if template inference is still desired, but do not infer template choice from prose. Mature systems overwhelmingly prefer explicit execution metadata because it survives replay and migration better.
- **Adopt:** Make output visibility conservative by default: a downstream step can only consume a producing step's outputs after that producing step reaches its terminal join. This mirrors GitHub's job-output model and avoids subtle races. If early consumption is needed later, make it an explicit advanced feature rather than an implicit side effect [5][17].
- **Avoid:** Do not import Temporal's full "user code must be deterministic under replay" burden into method authoring. Draft C's YAML-plus-runner model is a strength; forcing method authors into Temporal-style replay discipline would overcomplicate the product [1][2].
- **Avoid:** Do not copy GitHub Actions' string-heavy expression culture. Draft C is stronger when names resolve to typed artifact records instead of late-bound strings and magic contexts [5][6].
- **Avoid:** Do not default to Argo-style fail-fast for research, review, or comparison phases. Preserve sibling evidence unless the method explicitly opts into fail fast [11].
- **Avoid:** Do not let Claude Code specifics leak back into the domain through adapter shortcuts. Prior art consistently rewards keeping orchestration semantics above the adapter layer, even when the first adapter is the only one that exists today [1][15][18].
