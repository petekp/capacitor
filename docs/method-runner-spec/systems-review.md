# Systems Review

Draft C is directionally strong on the product shape: the method model is portable, attempt isolation is the right safety primitive, and event authority is the right long-term move. The draft is not yet operationally survivable as written, though, because several invariants live only as prose. In practice that means different adapters, projectors, or recovery paths could make different decisions from the same run history.

## Boundary Risks

1. Domain intent is still leaking through adapter template selection. In Draft C §2, steps only declare `action` plus optional `template` overrides (lines 82-95), but §5 then introduces "runner intent mapping" from semantic categories like research, implementation, and synthesis to Claude-oriented templates (lines 262-278). That violates the portability claim in §1 and §11 that templates are adapter choices, not domain concepts (lines 15-16, 483-506). If the runtime has to infer "this is a synthesis step" from prose or heuristics, different adapters will execute the same method differently. The portable layer needs an explicit, typed statement of step intent owned by the domain.

2. The handoff markdown contract is carrying too much portable meaning. §5 requires the header to name the expected handoff path and required sections (lines 250-257), then makes execution logic depend on parsed markdown fields like `verdict`, `completion_claim`, and `issues_found` (lines 361-373). §9 gates are then evaluated against those parsed relay fields (lines 448-455). That means the domain is not actually depending on a provider-neutral `WorkerResult`; it is depending on one Claude relay document shape. Replacing the Claude adapter would require emulating the markdown contract instead of implementing a typed result boundary.

3. The filesystem layout is at risk of becoming the real domain model. §3 says `.method/` is both the CLI runtime contract and the reference model for future Capacitor storage (lines 126-127), while §11 says Capacitor should treat YAML as import/export and persist structured runtime objects in Rust (lines 519-584). Those are compatible only if the path layout is explicitly an adapter serialization. As written, artifact identity, relay roots, and canonical copies are described in path terms first (lines 166-173, 294-300), so the CLI layout can easily ossify into the public architecture.

4. Output naming ownership is not cleanly separated. Method outputs are declared at the top level (lines 67-68), step outputs are also declared by name (line 89), interactive steps may emit outputs too (line 114), and the runtime output registry is keyed only by output name (lines 225, 385-387). That creates a boundary leak between local step-scoped production and run-global publication. Without a namespace or ownership rule, a step can accidentally collide with a method-level symbol or with a sibling's intermediate output.

5. The adapter boundary is named but not contracted. §11 says the Claude adapter is one implementation of `PromptBuilder + WorkerDispatcher + ArtifactIngestor` (line 506), but Draft C never defines the input/output contract for those interfaces. That leaves too much behavioral meaning in shell examples from §5 (lines 311-359). For a clean architecture split, the portable layer must own the interface semantics and error contract, not the first adapter implementation.

## Operational Concerns

1. `run.lock` exists, but lock scope is undefined. §3 says `locks/run.lock` prevents concurrent mutators (line 165) and §10 says resume begins by acquiring it (line 463). The same system also needs long-running worker watchers, handoff ingestion, retries, gate handling, and interactive responses. If one process holds the lock across the whole watch loop, interactive submissions and secondary controllers will deadlock. If the lock is meant to be short-lived, the spec needs to define the exact critical sections and write protocol.

2. There is no liveness policy for stuck workers. §5 waits for both terminal process state and a parseable handoff (lines 304-309). §10 says active workers are kept running on resume (line 467). A worker that never exits and never produces a valid handoff can therefore pin a run indefinitely with no timeout, heartbeat, stale-session rule, or operator override. Under real operation, this will happen more often than clean crashes.

3. The storage model will accumulate operational debt under retries and fanout. Each attempt keeps immutable prompts, bindings, parsed handoffs, canonical handoff copies, and output registry entries (§3, lines 166-173; §5, lines 361-373). That is good for auditability, but the draft contains no retention, pruning, or archival policy. Long methods, repeated retries, and parallel workers will make resume scans slower and disk growth unbounded.

4. Output registration is operationally ahead of schedulability. §6 makes outputs canonical records as soon as they are bound (lines 383-397), while §8 says completed-member outputs may be registered early but not consumed downstream until the producing join is terminal unless configured otherwise (line 433). That creates a confusing half-state: an output exists, appears in state, but is not actually ready. Operators and UIs will misread this unless readiness is modeled separately from existence.

5. Gate handling lacks an activation model. §9 says failed gates move the run to `waiting_for_gate` or `blocked` depending on whether human intervention can satisfy them (lines 450-453), but it does not define who can satisfy them, how reevaluation is triggered, or whether a gate failure can be superseded by newly produced evidence. In production, gates without explicit satisfiers become permanent parking lots.

## Failure Modes

1. Event authority and artifact durability can diverge during handoff ingestion. §4 says every mutation is first an event and then a projection (lines 179-216), but §5's actual workflow is detect handoff, copy artifact, parse it, register artifacts, bind outputs, and transition state (lines 361-373). §10 then rebuilds from `events.ndjson` plus immutable artifacts (lines 465-469). A crash between artifact copy and event append, or between event append and durable artifact persistence, yields a replay gap where the event log and filesystem disagree. The spec needs a transactional ingestion sequence, not just append-only intent.

2. `events.ndjson` has no corruption recovery story even though it is authoritative. §3 and §4 treat the file as append-only truth (lines 163, 179-188), and §10 rebuilds from it when `state.json` is stale (line 465). But the spec does not say what happens if the final line is torn, duplicated, truncated, or partially fsynced. One malformed tail record can make the entire run non-replayable unless there is an explicit last-good-sequence recovery rule.

3. Stale locks can brick a run. `run.lock` is central to resume safety (§3 and §10, lines 165 and 463), but there is no owner identity, lease timeout, heartbeat, or steal policy. Any crash in the lock holder can leave a run permanently "owned" by a dead process.

4. Handoff failure handling is too coarse for real recovery. §5 says exit without handoff is failure and handoff without terminal process state is still running (lines 304-309). It does not say what to do with duplicate handoffs, parseable handoffs missing required sections, corrected handoffs written after an initial parse failure, or handoffs from adapters that can only report partial status. Those are not edge cases; they are normal degraded states in a system that recovers from crashes and partial writes.

5. Retry and output supersession are not explicitly coupled. Retries allocate new attempt directories and old attempts are immutable (§10, lines 473-477), but §6 still says each output name resolves to one canonical record (lines 385-395). The missing rule is when a later attempt is allowed to supersede an earlier bound output, especially for `first-clean` and `merge-digests`. Without that, a stale output can remain canonical even after a corrective retry starts or completes.

6. Interactive responses have no idempotency or provenance rules. §7 records the response artifact and validates required fields (lines 401-409), but there is no protection against duplicate submissions, stale approvals, or responses from the wrong actor or UI surface. Once approvals and manual tests move into Capacitor, those become correctness issues rather than UX polish.

## State and Concurrency Concerns

1. The draft does not define a normative state machine even though it depends on one. §4 lists events and broad run statuses (lines 190-227), §5 defines worker-completion conditions (lines 302-309), §8 defines joins (lines 419-433), and §9 defines gate pauses (lines 448-453). What is missing is the allowed transition graph for run, phase, step, worker, and gate entities. Without that graph, replay is not deterministic because two projectors can derive different legal states from the same event stream.

2. `current_phase_ids` and `current_step_ids` are underpowered for parallel execution. In §4 they are treated as part of authoritative projected state (line 222), but §8 allows multiple eligible steps to run together and §9 allows one step or phase to be paused on a gate while siblings are terminal or still running. A pair of arrays cannot faithfully represent the frontier of a partially joined, partially blocked graph. They are useful UI hints, but they are not strong enough to be canonical state.

3. Monotonic `seq` implies a single event allocator, but the draft never names it. §4 requires every event to carry a run-local monotonic `seq` (line 183). §10 resume, §7 interactive submissions, and §11 runtime-service migration all imply multiple sources of new events over time (lines 407, 463-469, 513-517). Unless one component is explicitly the sole appender, concurrent writers will race on ordering and replay will become adapter-dependent.

4. Output resolution is currently race-sensitive. `first-clean` is defined in §6 as "take the first artifact with acceptable verdict and completion claim" (lines 390-395), while §8 registers outputs as soon as members finish (line 433). "First" here is wall-clock first, not definition-order first or causal-order first. That makes output choice nondeterministic under scheduler noise, especially once retries and runtime-service delivery latencies exist.

5. Completion policy, retries, and gates do not yet have a precedence model. The draft defines `all_complete`, `any_complete`, and `manual` at the schema layer (lines 66 and 93), step completion at the worker layer (§5, lines 304-309), phase joins in §8, and blocking gates in §9. It never states which rule wins when they disagree. A step can plausibly be "complete enough" for `any_complete`, still have a failing sibling, and then hit a step gate that fails. The spec needs one authoritative order of evaluation.

6. Replay and reconciliation are currently mixed together. §4 says `state.json` can be rebuilt solely from events plus immutable artifacts (line 229), but §10 resume also says the runner scans nonterminal workers, ingests new handoffs, and marks inactive/no-handoff attempts failed (lines 466-469). That means restart behavior is not pure replay; it is replay plus live filesystem reconciliation. The system should name those as distinct phases, otherwise event sourcing is only partially true.

## Migration or Observability Gaps

1. The migration target is described, but the adapter API is not. §11 usefully identifies the portable layer and the future runtime-service ownership model (lines 495-517), yet it stops before defining method signatures, callback lifecycles, or failure classes for `PromptBuilder`, `WorkerDispatcher`, and `ArtifactIngestor`. That makes the CLI behavior the de facto spec, which is exactly what the portability section is trying to avoid.

2. Only YAML has an explicit version field. §2 defines `schema_version` for the authoring format (line 58), but there is no versioning story for event records, `state.json`, parsed handoff JSON, output artifact records, or gate instances. A system that intends to migrate live runs from CLI mode into Capacitor needs upcasters and compatibility rules for the runtime data model, not just the input schema.

3. Observability is event-shaped but not operator-ready. §4 lists event kinds but leaves `payload` effectively unconstrained (lines 181-216). There is no required telemetry for dispatch latency, retry reason taxonomy, parse-failure class, gate wait duration, lock contention, scan duration, or worker-runtime age. Without those fields, Capacitor can display progress, but it cannot explain why a run is stuck or regressing.

4. Human intervention is not auditable enough for a first-class runtime. Interactive responses become runtime artifacts in §7 (lines 401-411), and gates can be satisfied by human action in §9 (line 452), but the model does not require actor identity, source surface, or decision timestamp beyond the coarse event timestamp. Once approvals move into the UI, provenance is part of correctness.

5. Artifact identity is still too path-centric for the runtime-service future. Input digests reference canonical artifact paths in headers (§5, lines 255-260), worker state stores `relay_root` and handoff paths (§4, line 224), and runtime mapping in §11 still describes artifacts in terms that assume path-backed refs (lines 526-529). Capacitor needs stable artifact ids that survive relocation, replication, or storage backends other than the CLI filesystem.

6. Swift projection is named, but consistency semantics are missing. §11 says Rust should own canonical state and Swift should project it into glanceable UI (lines 517-531). What is absent is the query or subscription contract: whether Swift reads snapshots, streams ordered events, or consumes a hybrid. Without that, migration from `state.json` polling to runtime-service-native projection risks subtle UI races and "stale but looks current" failures.
